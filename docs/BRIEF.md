## 2. Product principles

1. **Self-service first.** Most debtors should resolve their case without talking to a human.
2. **Legal rules are enforced by the engine,** so no flow, template or user can break them. **We implement what the law requires and nothing more.**
3. **Every number comes from the ledger and the calculation engine.** Amounts are never typed, guessed or generated by an LLM.
4. **Configurable per claim type and portfolio.** Calculation rules, strategies, fees, payment-plan envelopes and templates vary by claim type, client and portfolio.
5. **Fast portfolio boarding** is a competitive weapon: a new tape should go live in hours, not weeks.
6. **Efficiency.** Choose the simplest thing that works. Avoid infrastructure we don't need yet.

### 3.2 Data model and portfolio onboarding

**Two layers.** The EU NPL template is a *transactional* data template: a snapshot built to sell a bank portfolio. Servicing needs much more. So the data model has two layers:

**Layer 1 — Transaction layer (EU NPL template).** Commission Implementing Regulation (EU) 2023/2083: Annex I templates, Annex II data glossary, Annex III instructions. It is used to board bank portfolios and to export data tapes (portfolio sales, FCT reporting, data rooms). In Phase 0:
1. Download the sources into `docs/reference/eba/`:
   - Binding legal text (source of truth): EUR-Lex, `https://eur-lex.europa.eu/eli/reg_impl/2023/2083/oj` (CELEX 32023R2083). Get the HTML and the PDF, including the annexes.
   - Machine-readable Excel annexes (Annex 1 templates, Annex 2 glossary) from the EBA page: `https://www.eba.europa.eu/legacy/regulation-and-policy/regulatory-activities/credit-risk/implementing-technical-standards-npl`. These files are attached to the EBA's final report of Dec 2022. The adopted regulation follows that report in all major respects.
   - Fallback: the Commission's documents register for C(2023)6306 (annex files `C(2023)6306_1` to `_3`).
   - Use `curl`/`wget` with retries. If a site is blocked by the allowlist, tell me the domain to add (expected: `*.europa.eu`). Don't reconstruct the template from memory.
2. Record each file's URL, retrieval date and SHA-256 in `docs/reference/SOURCES.md`.
3. Parse the files into a **field catalogue** (`docs/reference/eba_field_catalogue.csv` plus a generated typed model): entity/tab, field ID, name, definition, data type, allowed values, mandatory/optional per portfolio type. Where the Excel and the EUR-Lex text differ, follow EUR-Lex and log the difference. **Do not invent template fields.**

**Layer 2 — Operational servicing layer.** The canonical model the platform runs on: a superset of the template, enriched with everything day-to-day servicing needs.
- **Gap analysis first** (`docs/reference/eba_gap_analysis.md`): for each module of this brief, list what the template lacks, then design the extensions. Typical gaps:
  - event-level transaction history after the cut-off date
  - claim type, rule pack and rate history (§3.3)
  - multiple contact points with source, validity and per-channel consent
  - communication log with evidence, and flow state
  - promises to pay, payment plans, disputes and complaints
  - holds with their legal basis
  - legal and bailiff procedures and costs
  - document index, debtor portal identity
  - client mandate terms, commissions and remittances
  - ownership/servicing history
- **Non-bank claims** (invoices, rents, private loans, judgments) don't fit the bank template. They board through the generic mapper directly into Layer 2.
- **Mappings in both directions:** template → operational on boarding; operational → template export, so a compliant tape can be regenerated at any date.

**Boarding pipeline:**
- **Inputs:** EU-template tapes, any other CSV/XLSX/fixed-width file, multi-file tapes (debtors, accounts, transactions, schedules, collateral, documents).
- **Steps:** upload → profiling (types, nulls, distinct values, patterns) → **LLM-proposed mapping** to the canonical model, with confidence and rationale per field → human review UI → declarative, versioned transformations (French date/decimal formats, SIREN/SIRET, IBAN, E.164 phones, address normalisation via the national address API (BAN); ask me to allow its domain when needed) → claim type assignment → validation rules (blocking vs warning) → **data-quality report** (completeness, contactability %, reconciliation of balances against the seller's cut-off totals) → staging → commit as a versioned *boarding batch*, reversible until confirmed.
- Mapping profiles are saved per seller/client and reused.
- Scale: stream-process large tapes in a Python worker (Polars/DuckDB), not in Edge Functions. Test at 50k rows in CI; benchmark 1M rows within the VM's memory.
- Bulk document upload (zip): auto-link to accounts by reference, OCR plus structured extraction.

### 3.3 Claim types and calculation engine (bank credit vs civil claims)

Interest, fees and balances don't accrue the same way for a bank loan and for a civil or commercial claim. Each claim therefore carries a **claim type** and a versioned **rule pack**, and one engine applies the right rules to each.

**Claim types** (extensible by configuration):
- **Bank credit:** consumer instalment loan, revolving credit, overdraft, BNPL/split payment, mortgage, professional/SME loan.
- **Civil and commercial claims:** B2B invoice, B2C invoice or subscription (telecom, energy, services), rent and charges, private loan between individuals, judgment debt (enforceable title).

**A rule pack defines,** with effective dates and legal references:
- **Balance components** and how each evolves: principal, unpaid instalments, capital outstanding after acceleration, contractual interest, late interest, insurance, fees, indemnities, procedure costs.
- **Interest basis:** contractual rate (fixed or index + margin), legal interest rate (two rates set every six months, depending on the creditor's status), B2B late-payment rate. Rate tables keep their full history, so any past date can be recomputed.
- **Start events:** due date, *déchéance du terme* (acceleration), *mise en demeure*, judgment date. Includes the +5-point increase of the legal rate two months after a judgment becomes enforceable.
- **Day-count convention and accrual frequency,** taken from the contract.
- **Capitalisation** (*anatocisme*): allowed or not, and under what conditions (interest due for at least a full year, provided by contract or court decision). Excluded where the law or case law excludes it (e.g. consumer credit — to validate).
- **Caps and allowed fees:** consumer-credit default indemnity under the decree scale, €40 B2B indemnity, no collection fees without an enforceable title.
- Prescription/forclusion periods and the payment allocation order.

**Bank-loan specifics:**
- Import or rebuild the amortisation schedule (*tableau d'amortissement*).
- Separate unpaid instalments from capital outstanding.
- Handle acceleration, variable rates and insurance premiums.

**Engine requirements:**
- **Deterministic and reproducible.** The balance at any date is recomputed from ledger events + rule pack + rate tables. No stored running totals that can't be explained.
- Produces an **itemised statement of account** (*décompte*) explaining every line. It is used in letters (R124-4 breakdown), the portal, client statements and bailiff files.
- Rule packs are **data** (versioned config with legal references), not code branches. Adding a claim type = adding a rule pack + tests.
- Tested with property-based tests and **golden cases** I validate. Ask me for anonymised real examples per claim type.

### 3.4 Servicing core: accounts, ledger, payments
- **Entities:** Client, Portfolio, Account (*créance/dossier*) with claim type and contract terms, Debtor (consumer / professional natural person / legal entity), co-debtors and guarantors, contact points, collateral, documents, **claim ownership history** (original creditor, current owner, servicer, mandate type), applicable legal regime (contract date matters, see §4).
- **Double-entry, append-only ledger.** Interest accruals are posted by the calculation engine. Corrections are made by reversal. Money is stored as integer minor units plus currency, rates as Decimal, never floats.
- **Payment allocation waterfall** from the rule pack, overridable per client/portfolio where the law allows.
- **Payments:** card, SEPA direct debit, SEPA transfer with structured reference. Bank-statement reconciliation (CAMT.053). Remittance runs (*reversements*) and statements to clients net of commission. Commission invoicing.
- **Payment plans** (*échéanciers*) inside a client-defined envelope (max duration, min instalment, settlement/discount authority), promises to pay, broken-promise detection.
- **Holds** that freeze outbound activity: dispute, *surendettement*, *procédure collective*, deceased, wrong party, recalled by client.

### 3.5 Collection flow builder and engine (key feature)
- **Visual editor** (React Flow) per portfolio, claim type or segment. Node types:

  - wait (duration / until date / until event)
  - condition (any account, debtor, claim-type or engagement attribute, score band)

- Optional per-flow settings (business choices, not legal requirements): contact frequency caps, sending windows, budget caps.
- **Legal guardrails checked before every outbound action, which flows cannot override:** holds, channel consent, mandatory mentions (see §4).

### 3.6 Omnichannel communications (every channel that has an API)

**Channel-agnostic messaging layer.**

**Target catalogue:** email, SMS, RCS, WhatsApp, Telegram, Facebook Messenger, Instagram messaging, Apple Messages for Business, Viber, voice (outbound calls, IVR, voicebot), push notifications, portal web chat, simple and registered postal letters (including hybrid), qualified eIDAS LRE. Add any other channel that exposes an API.

**Platform policies are a business risk, not a blocker.**

- Build every channel in the catalogue, **WhatsApp included**. Record each platform's policy status in `docs/CHANNELS.md` as information only.
- **Resilience:** detect when a channel account is restricted or a template is rejected, alert ops, and have flows automatically fall back to the next allowed channel. No channel is a single point of failure.

  - Telegram: bots can only message users who started the bot first, so opt-in goes through a portal deep link.

**Build approach:**

- **Unified inbox:** inbound messages from every channel land in one debtor timeline and go through AI triage.
- **LRE rule:** for non-professional recipients, send LRE only with prior consent. Otherwise fall back to paper registered mail.
- **Templates:** locked legal blocks + editable copy + variables bound to the ledger/décompte, rendered per channel format. French first. Store the exact rendered content and delivery proof of every message.
- **Priority:** email, SMS, WhatsApp, letters/LRE and portal chat first. Then the other channels in the order proposed in `docs/CHANNELS.md` (reach in France, cost). Ask me to confirm.

## 4. Legal requirements (and only these)

**Rule: implement what French/EU law requires for phase A, nothing more.** No certifications, no "best practice" frameworks, no voluntary codes. For each item, `docs/COMPLIANCE.md` lists the legal reference, the enforcement point in the code, and a "to validate by counsel" flag. If you think something is legally required but are not sure, put it under "Open questions" instead of building it. Never invent legal rules.

**Third-party amicable collection** (Code des procédures civiles d'exécution, art. L111-8, R124-1 to R124-7):
- Store the written agreement terms with each creditor (R124-3).
- Funds collected for creditors go to a dedicated account (R124-2). The ledger keeps client money separate.
- The first letter to the debtor contains all R124-4 mentions, including the breakdown of principal/interest/accessories and the reproduction of L111-8 paragraphs 2–3. Implement this as a locked template plus a pre-send validator. Archive the sent letter, because the collector must be able to prove it was sent with all mentions.
- Issue a receipt (*quittance*) for every payment (R124-6).
- No recovery fees charged to the debtor without an enforceable title (L111-8). Block this in the ledger.
- No document resembling a judicial or bailiff act (Code pénal art. 433-13).

**Interest, fees and balances** (encoded in rule packs, §3.3):
- Late interest at the legal rate from the *mise en demeure* for sums of money (Code civil art. 1231-6).
- Legal interest rates and their six-monthly publication (Code monétaire et financier art. L313-2), and the +5-point increase two months after a judgment becomes enforceable (L313-3).
- Capitalisation only under Code civil art. 1343-2. Check whether case law excludes it for consumer credit.
- Consumer-credit default: acceleration, interest at the loan rate and an indemnity capped by decree, no other fees (Code de la consommation art. L312-38, L312-39 and their decree). Same exercise for the mortgage-credit equivalents.
- B2B claims: late-payment interest and the €40 flat recovery indemnity (Code de commerce art. L441-10).

**Holds required by law:**
- *Surendettement* (Banque de France): suspension of enforcement once the file is declared admissible.
- *Procédure collective*: individual actions and payments of prior debts are stopped.

**Consumer credit / BNPL:** CCD2 transposed by ordonnance n° 2025-880, applicable from 20 Nov 2026; contracts already running stay under the old rules. Each claim carries its applicable legal regime, and article numbers must be checked for contracts under the new regime.

**Electronic registered mail:** a non-professional recipient must have consented beforehand (Code des postes et des communications électroniques, art. L100).

**GDPR / Loi Informatique et Libertés:**
- Information to debtors whose data we did not collect from them (GDPR art. 14). Include it or a link in the first communication.
- Legal basis per processing; retention limits with automated purge; data-subject rights (access, rectification, erasure, objection) handled in the back-office.
- Security appropriate to the risk (art. 32): encryption at rest and in transit (Supabase default), access control, MFA for staff.
- No solely automated decision with legal or similarly significant effect (art. 22). AI suggests; rules or humans decide on settlements/escalations.
- Lawful transfers if a sub-processor (LLM API, messaging platform) is outside the EU (GDPR ch. V).
- Tracking pixels in emails need prior consent (art. 82 Loi Informatique et Libertés, as applied by CNIL délibération n° 2026-042 of 12 March 2026).

**AI Act:** don't build anything that falls into a high-risk category (e.g. creditworthiness scoring of natural persons). If a feature would, flag it to me before building.

**Deferred until the ACPR application (phase B):** credit-servicer governance, internal control, LCB-FT, regulatory reporting. Don't build these now.

*Platform policies (WhatsApp, Telegram, etc.) are not law. They are tracked in `docs/CHANNELS.md` (§3.6), not here.*

## 6. Stack: Supabase-based

**Supabase is the foundation:** Postgres, Auth, Storage, Queues (pgmq), pg_cron, Row Level Security.
- The hosted project will live in a **specific EU region: Paris (`eu-west-3`)**, not the "Europe" general region (which can land outside the EU).
- Development and CI run on the **local Supabase stack** (Supabase CLI + Docker): SQL migrations in `supabase/migrations`, `supabase start`, seed scripts, type generation, `supabase test db`.
- Deployment: Supabase GitHub integration applies migrations on merge to `main` (see §0).

**Frontend:** Next.js + TypeScript + `@supabase/ssr`, React Flow (flow builder), Tailwind + shadcn/ui. Three surfaces: back-office, client portal, debtor portal. Hosting TBD (ask me); server functions must run in an EU region.

**Worker service:** Python 3.12 (uv), containerised, EU-hosted (ask me which host). Connects to Supabase Postgres directly. It runs:
- heavy jobs: tape ingestion (Polars/DuckDB), document processing
- the **calculation engine** (interest accruals, statements of account)
- the flow-engine executor
- channel adapters and provider webhooks
- the AI gateway and decisioning

**Flow engine, Postgres-native (no Temporal for the MVP):**
- Each account in a flow has a persisted state row with `next_run_at`.
- A pg_cron tick enqueues due steps into Supabase Queues.
- Idempotent workers execute them (idempotency key per step).
- Write an ADR on when to revisit this choice.

**Edge Functions:** only for small, short tasks, with regional invocation pinned to Paris. No core business logic there. They have tight memory/CPU/duration limits, and we want to stay portable.

**Security model (non-negotiable):**
- RLS enabled on every table in exposed schemas.
- Ledger, payments, communications and boarding tables are writable only by the worker (service role) or by `SECURITY DEFINER` Postgres functions, never directly from the browser through the auto-generated API.
- The service-role key never reaches the client.
- pgTAP tests prove tenant isolation.

**Portability:** plain SQL migrations and standard Postgres features in core logic, so we can move to self-hosted Supabase or plain Postgres if a bank client requires it.

**Payments:** a regulated PSP (e.g. Stripe, GoCardless) in test mode. **Every external provider (payments, every messaging channel, postal, LRE, bailiffs) gets a sandbox/mock adapter,** so the whole system runs locally with zero real sends or payments.
